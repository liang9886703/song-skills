# 检查项详细标准（供校验时参考）

> 本文件为 Skill质量校验官 的详细检查标准参考，包含每项指标的通过标准、典型缺陷和检查方法。

---

## 维度1：结构完整性 S（4项 · 权重25%）

### S01 — 是否有明确的 name 和 description？
- **通过标准**：SKILL.md front matter 中 `name` 和 `description` 均存在且非空；`description` 包含功能概述和至少一个触发关键词
- **典型缺陷**：只有 name 缺少 description；description 为空串或纯占位符
- **检查方法**：解析 YAML front matter 的两个关键字段

### S02 — 是否有全局约束/铁律？
- **通过标准**：有独立的约束条款章节（标题包含 约束/铁律/原则/红线 等），且至少涵盖一条不可违反的核心行为限制
- **典型缺陷**：没有说明核心原则；约束散落在步骤中但缺少汇总章节
- **检查方法**：搜索文档中是否存在以 约束/铁律/原则/重要提示/注意事项 为主题的独立段落

### S03 — 是否有工作流程总览？
- **通过标准**：有流程图（ASCII/Mermaid）或有编号的步骤概览列表，读者能在30秒内理解全貌
- **典型缺陷**：只有零散的详细步骤而无整体视图；步骤编号缺失或不连续
- **检查方法**：查找 流程/Flow/Workflow/步骤概览 相关的图表或有序列表

### S04 — 引用的外部文件是否真实存在？
- **通过标准**：SKILL.md 正文中引用的所有 `references/*.md`、`scripts/*.*`、`config/*.*` 文件在对应路径下真实存在；无幽灵引用
- **典型缺陷**：正文写了 `> 参考 references/api-summary.md` 但该文件不存在；引用了 `scripts/run.sh` 实际目录中只有 `run.py`
- **检查方法**：
  1. 从 SKILL.md 提取所有 `references/`、`scripts/`、`config/` 路径引用；对每个引用逐一验证:
     - 能 `ls`/能 Glob 目标目录, 文件名在列表内? **🔹 通过** ✅
     - 能 list 目录但无该文件? **🔴 Ghost Ref.** ❌ (如 references/api.md 写成 ref.md)
     - List 被拒(PermissionDenied)? **🚮 [未验证]** (SANDOX / AUTH LIMIT)
     - 目标目录根本不存在(No such file)? **🔴 Path Err.** ❌

## 维度2：逻辑一致性 L（4项 · 权重20%）

### L01 — 步骤间数据流是否衔接？
- **通过标准**：上一步骤声明的输出变量/产物是下一步骤引用的输入；不存在悬空的输入依赖
- **典型缺陷**：步骤2 需要 data_X 但步骤1 未产出到该名称；某变量的值从未被消费
- **检查方法**：提取所有步骤的 input/output 描述，构建依赖图并检测断链

### L02 — 超时/重试配置是否统一？
- **通过标准**：超时阈值和重试次数定义在一处（front matter 变量 / config 文件 / 开头常量），正文仅引用变量名
- **典型缺陷**：同一类操作的超时值在不同步骤中硬编码了不同数字
- **检查方法**：全文检索 timeout/retry/retries/delay/max_attempts 等关键字的赋值语句，比对一致性

### L03 — 步骤间是否存在循环依赖？
- **通过标准**：将步骤视为节点、数据依赖视为边构成的有向图是无环的 (DAG)
- **典型缺陷**：Step A 产出需 Step B 先完成，而 Step B 又需 Step A 的产出——形成死锁
- **检查方法**：
  1. 提取所有步骤的依赖关系（如 "Step 2 需要 Step 1 的产出X"）
  2. 构建有向图：节点=步骤，边=数据流向（A → B 表示 B 依赖 A 的产出）
  3. 使用拓扑排序检测环：若无法生成合法拓扑序列，则存在循环依赖
  4. 环的典型表现：A→B→C→A（三步首尾相接形成闭环）
- **示例**：正常链路 Step1→Step2→Step3（无环 ✅）；死锁链路 Step1→Step2→Step1（有环 ❌）

**依赖关系识别规则**：
- 显式依赖：步骤中写"使用步骤X的产出"、"基于上一步的结果"
- 隐式依赖：步骤中引用了上一步定义的变量名（如 `$WORKSPACE/tmp/xxx`）
- 顺序依赖：步骤编号本身暗示执行顺序（Step1 → Step2 → Step3）
- *若无法从文本中提取依赖关系，默认按步骤编号顺序视为线性依赖（无环）*

### L04 — 条件分支是否覆盖全部可能路径？
- **通过标准**：if/else 或 switch 分支涵盖了正常路径 + 所有已知的异常分支 + 兜底 else/default
- **典型缺陷**：「如果成功则…」之后没有对应失败处理；多选一条件遗漏了某种取值
- **检查方法**：统计文中的 if/elif/case 判断及其对应的 else/fallback/default 子句数量

## 维度3：鲁棒性 R（5项 · 权重20%）

> **适用性说明**：R01-R05 均假定被检 Skill 涉及并行时外部操作（API/数据处理/超时配置等）。**若被检 Skill 是纯提示词型（无 scripts/config/references），本维度所有项标记为 "➖ 不适用" 而非默认通过，分子分母同时扣减，不入总分。**

### R01 — 外部接口调用失败是否有降级方案？
- **通过标准**：每次外部 API/CLI/服务调用均有 try-catch + fallback 行为描述（如 "接口A超时时使用缓存B"）
- **典型缺陷**：只写了"调用xxx"，没有任何异常捕获或替代策略
- **检查方法**：定位所有 curl/API call/subprocess/shell 执行点，逐一查验后续有无错误处理段。降级逻辑可能存在于以下三处，需综合检索：
  1. SKILL.md 正文中（如 "若接口A失败，则使用接口B" 的文字说明）
  2. scripts/*.py 脚本中（如 `try: ... except: ...` 代码块或 fallback 函数调用）
  3. config.json 或其他配置文件中的 fallback 配置项（如 `"fallback_endpoint": "..."`)
  - 若三处均无降级痕迹，判为 ❌

### R02 — 数据为空/null 时是否有兜底展示？
- **通过标准**：面向用户的输出字段有空值填充策略（如显示「暂无数据」「—」「N/A」而非留白或 null 字符串）
- **典型缺陷**：模板中 `${variable}` 直接拼接而 variable 可能 undefined
- **检查方法**：追踪最终渲染给用户的内容中的动态插值点，看其前方是否有空值守卫

### R03 — 关键字段缺失时是否有合理默认值？
- **通过标准**：从外部获取的结构化数据的必要字段均声明了 default 值或在代码中有兜底赋值
- **典型缺陷**：JSON path 如 `data.result.items[0].id` 无防空访问导致 KeyError/IndexError
- **检查方法**：识别对外部返回值的字段提取表达式，逐个核查安全访问方式

### R04 — 操作超时是否有明确处理机制？
- **通过标准**：涉及网络请求、长耗时计算等操作的环节设定了 timeout 上限及到期后的行为（取消并继续/报错退出/换源重试）
- **典型缺陷**：无限等待外部响应；timeout 参数未设置
- **检查方法**：结合 L02 已检出的超时常量，进一步核实其配套行为描述是否完整

### R05 — 单模块失败是否会阻断整体流程？
- **通过标准**：非核心模块的错误不会中断主流程；主流程的关键路径与非关键可选路径解耦
- **典型缺陷**：一个辅助信息查询接口挂掉→整个 Skill 无法运行到结尾
- **检查方法**：审视每个外部调用的 error branch 是 continue 还是 abort

## 维度4：可执行性 E（4项 · 权重15%）

### E01 — 指令措辞是否唯一确定、无歧义？
- **通过标准**：每一个祈使句只有一个合理的解读方向；避免副词修饰语（适当、尽量、尽快）单独充当限定
- **典型缺陷**：「适当处理后继续」→ 怎么算适当？「尽量收集更多信息」→ 收集多少算够？
- **检查方法**：扫描全文中含有 适当/尽量/尽可能/酌情/视情况/if needed 类模糊表达的位置

### E02 — 关键输出格式是否有示例？
- **通过标准**：对于表格、Markdown、JSON 等结构化输出，提供了完整的格式范例（包括表头名、分隔符、缩进层级）
- **典型缺陷**：只说了"输出一张表格"，没给列名和对齐方式的样例
- **检查方法**：找到所有指定输出格式的命令，核对其后方有没有紧跟 Example/Demo/示例 段落

### E03 — Shell/脚本命令是否完整带参数？
- **通过标准**：提及的所有 shell 命令都给出了完整形式（程序名 + 所有必要参数 + 至少一组合法参数值示例）；不出现裸动词
- **典型缺陷**：「运行脚本生成结果」→ 哪个脚本？什么参数？「启动服务器」→ 用哪个端口？
- **检查方法**：抽取正文中所有的 shell/command/script 引用语块，验证其完整性和可直接复制执行的属性

> **与 Step 2.5 的区别**：
> - Step 2.5：检查脚本文件本身的语法正确性（import、括号、缩进等）
> - E03：检查 SKILL.md 正文中引用的 shell/command/script 命令是否完整可执行
> - 两者独立，互不影响。

### E04 — 条件数值阈值是否有明确定量？
- **通过标准**：凡是涉及大小比较的数量门槛均为确切数（≥10次、≤500ms、>80%）而不是定性形容词
- **典型缺陷**：「等待较长时间」「收集大量样本」「频率过高则限流」→ 何谓较长？何谓大量？何谓过高？
- **检查方法**：全文搜索 > < ≥ ≤ > 大于 小于 超 高 低 快慢 长 多少 等比较语境，核对定量依据

## 维度5：无冗余 D（2项 · 权重10%）

### D01 — 同一语义规则是否仅在单一位置出现？
- **通过标准**：同一条行为规范、同一个技术细节不在两处及以上分别陈述（允许一处详述另一处交叉链接引用）
- **典型缺陷**：相同的 API base URL 写在了步骤2和步骤7的两处硬编码里；同一段约束文字出现在开头和末尾
- **检查方法**：对比疑似重复的自然语言段落和技术参数出现次数

### D02 — 是否清除了临时标记和遗留调试逻辑？
- **通过标准**：正文中不含 `待办`/`FIXME`/`HACK`/`XXX`/`TEMP` 等标记；scripts 目录下无 debug-only 入口函数、print 断言、注释掉的旧版代码超过连续3行
- **典型缺陷**：残留 `# 待办: 替换成正式API`；测试用的 `print("=== DEBUG ===")` 散落其中
- **检查方法**：grep `待办` `FIXME` `HACK` `XXX` `TEMP` 以及过长的注释块(>3行)

## 维度6：可维护性 M（2项 · 权重10%）

### M01 — 运行时可变配置是否集中在固定区域？
- **通过标准**：API endpoint、thresholds、file paths、feature flags 等可在部署时调整的值统一定义于 front matter 区段或专用 config 文件内，业务逻辑区仅引用这些名字
- **典型缺陷**：base_url 直写在第3步的一个 curl 里；retry_count 出现在第2步和第8步各自不同的字面值
- **检查方法**：列出所有可辨识的外部依赖型字符串和魔法数字，归类它们的出现模式

### M02 — 同一配置值是否只需在一处修改即可生效？
- **通过标准**：任一可配参数的全生命周期维护成本 = 改一行；即不存在 N 处同步更新的风险
- **典型缺陷**：timeout=30 同时写在 SKILL.md 正文和 scripts/run.sh 两处，改了一处忘改另一处就产生不一致
- **检查方法**：承接 M01 结果，计算每种配置属性的物理存储副本数
