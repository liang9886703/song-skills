# 阅读项目仓库

本 skill 主要规定最终分析报告的内容范围、结构、Markdown 格式、表达和讲述方式。根据用户的需要选择对应约束，信息获取方式由 Agent 按任务与环境自行决定。

## Skill 的维护原则

修改本 skill 及其 reference 时，优先写清最终文档应该呈现什么、怎样组织和表达、哪些内容需要省略。信息来源、工具选择、阅读顺序、检索策略和验证方式不设固定限制；不要把一次任务采用的探索方法固化为后续任务必须遵守的流程。

Agent 可以按需要阅读源码、查询文档或仓库元数据、检索外部资料及进行运行验证，具体操作遵循用户当次授权和环境权限。报告中的事实准确性、证据可追溯性和未确认边界仍需满足要求。

## Markdown 格式

最终报告的每个标题都必须带阿拉伯数字序号，并保留 `#`、`##`、`###` 等真正的 Markdown 标题语法。序号与标题层级对应：一级标题使用 `1`、`2`、`3`，二级标题使用 `1.1`、`1.2`，三级标题使用 `1.1.1`，更深层级依此递进；同级连续编号，子级随所属父级重新起算。例如 `# 9 主体对话数据流`、`## 9.1 第一次开始对话`、`### 9.1.1 输入处理`。新增、删除或移动章节时，同步更新受影响的序号、目录和章节引用。有序列表只用于短步骤或顺序条目，不用 `6.`、`6.1` 这样的普通段落承载整章。代码与结构示例使用带语言标记的围栏代码块，标题和列表前后保留空行。

## 如何选择约束

先判断用户需要初步了解整个项目、分析单个能力，还是深入分析整个项目，再选择约束：

- **初步了解整个项目仓库** → 读 `reference/first-understand-project-repository.md`。
- **了解仓库里的一个子能力** → 读 `reference/one-ability-analyze.md`。
- **用户明确要求深入分析整个项目仓库** → 先确认仓库类型，再按下表读取该类型的深入分析约束。
- **用户只丢了一个链接或目录（没说具体要什么）** → 默认按初步了解处理，读 `reference/first-understand-project-repository.md`。

### 按仓库类型选择深入分析约束

只有“用户明确要求深入分析整个项目”和“仓库属于对应类型”同时成立，才使用该类型的深入分析约束。仓库类型应结合项目说明、实际入口和核心实现判断；提到 Agent、Session 或数据流等名词本身不构成路由条件。

| 仓库类型 | 深入分析约束 |
| --- | --- |
| Agent 框架 | [Agent 框架深入分析](reference/deep-analysis/agent-framework-analyze.md) |
| Agent 策略（通过角色提示词、skills、tools、plugins 和配置组织既有运行时的行为） | [Agent 策略深入分析](reference/deep-analysis/agent-strategy-analyze.md) |

各类项目的深入分析约束统一放在 `reference/deep-analysis/` 下，后续增加项目类型时，在该目录新增对应文档并补充上表。尚无对应类型约束时，按用户的深入分析目标组织报告，不套用其他类型的模板。

## 深入分析的组织层次

深入分析的第一章统一为“深入分析代码范围”，声明本次选定的部署、启动方式、业务版本和核心链路，说明纳入与排除的实现及依据。同一报告目录已有该项目的初步报告时，利用其中的运行方式与版本信息帮助选定范围，并以当前代码接线确认；没有时不强制补写初步报告。默认深入当前实际使用的核心链路，不同时展开仓库中的所有版本与可选能力；用户指定多套对比时分别明确范围。后续内容严格遵守首章，范围变化须同步更新全文。

Agent 框架报告依次呈现：深入分析代码范围、名词表、自然语言基本流程、接口语义、代码文件结构分析、进程实例、组件对象、数据对象、主体对话数据流，再按需补充设计与证据边界。组件对象从所选进程的最上层装配根及独立全局 / 静态控制状态展开，标题按真实生命周期归属逐层组织；共享借用、跨树调用和接口实现关系另行标明，不因持有引用就虚构所有权或继承。每个对象交代父级、实例数量、创建与释放责任；操作说明按内容选择结构图、短伪代码或自然语言。数据对象按主体及内部子项介绍结构、主要操作和对象关系，不另设对象关系章。详细对话流以真实函数体和删节后的源码核心语句呈现：赋值、分支、循环、构造和入队直接使用代码语法，中文注释解释业务含义；关键对象与前文对应，各业务步骤标源码行范围，异步发送与接收分别展示。详见框架约束。

进程实例章节必须分别说明源码归属、使用者的安装与部署责任、启动和关闭方、通信方式。区分本仓库实现的进程、外部安装但由项目启动的程序、另行运行的网络服务和进程内依赖；已有托管服务与使用者自行部署的服务分别说明。这是各项目分析报告的通用呈现要求，不仅用于某次报告。

Agent 策略仍以职责明确的文件及装配、引用和协作为分析单位，遵守首章范围，不将框架的数据类型定义、函数伪代码格式和固定章节套用到策略文件；具体呈现按策略约束。共享对象完整介绍一次。

## 深入分析报告的依据与表达

能力与机制结论须有可核验依据，区分当前实现、文档设计意图、运行观察和推断；无法确认的行为明确保留边界。正文聚焦对象、关系、机制与业务流程，默认不堆放测试命令、控制台日志、通过率或验证输出附录。验证所得的必要结论可简述适用条件与证据，用户明确要求验证报告时按其要求展开。

## 默认目录约定

### 代码仓库

- 本地代码的默认根目录是 `$HOME/github/`，不要把用户目录硬编码成某个具体用户名。
- 用户指定本地目录时，以该目录的代码版本为分析对象；已有对应仓库时复用其位置。
- 需要下载仓库且用户未指定位置时，默认放在 `$HOME/github/<仓库名>/`。是否克隆、是否浅克隆、是否直接通过远端工具获取信息，由 Agent 根据任务决定。
- 报告注明实际分析的仓库、分支或提交，以及影响结论的本地改动；仅取得部分源码、浅克隆历史或其他有限证据时，说明对结论的影响。

### 调研文档

- 默认只产出 Markdown（`.md`）文档，并写入用户指定的路径；用户未指定路径时，才按下面的默认目录约定确定路径。
- 除非用户当次明确要求，否则不要生成 PDF、HTML、DOCX、图片或其他导出版本，也不要因为历史偏好、其他 skill 或常见交付习惯而额外生成这些产物。
- 默认文档根目录是 `$HOME/github/blogV2/data/content/`。
- 用户未指定输出路径时，调研文档放进 `$HOME/github/blogV2/data/content/` 下语义明确的子文件夹，不直接写在该根目录；用户指定路径时使用指定路径。
- 按能力或主题调研时，文件夹使用能力或主题名，例如 `$HOME/github/blogV2/data/content/coding-agent-记忆能力/`。
- 按项目调研时，文件夹使用项目名，例如 `$HOME/github/blogV2/data/content/hermes-agent/`。
- 同一项调研产生的主文档、分项目文档、图片和导出文件统一放在这个文件夹内。跨多个项目研究同一能力时，优先使用能力或主题名作为文件夹名，并把各项目文档与汇总文档放在同一文件夹中。
- 目标文件夹不存在时先创建，再写入文档。

## Coding Agent 项目分类约定

当用户使用下面这些集合称呼时，默认按对应项目展开，不必再次询问范围：

- **Coding Agent**：`codex`、`opencode`、`pi`、`claw-code`、`mycc`、`deepseek-harness`、`kimi-code`、`qwen-code`、`goose`、`maka`、`grok-build`、`cline`、`kilocode`
- **Agent 产品**：`hermes-agent`、`openclaw`、`open-design`、`openagents`、`multica`、`warp`
- **Agent 基础设施**：`ruflo`、`ax`、`litellm-agent-control-plane`、`OpenShell`
- **Agent 增强**：`oh-my-claudecode`、`oh-my-codex`、`oh-my-openagent`、`oh-my-pi`、`superpowers`

这些分类用于确定默认调研范围，不代表互斥的技术定义。用户明确点名、增删项目或另行限定范围时，以当次要求为准。

## 报告中的项目地址

- 每个项目产出的报告都必须在正文开头明确写出该项目的 GitHub 地址，统一使用格式：`项目地址：<GitHub URL>`。
- 地址必须有可核验的仓库信息支持，例如用户提供的链接或 Git remote，不得凭项目名猜测；SSH remote 应转换为便于读者访问的 `https://github.com/<owner>/<repo>` 形式。
- 一次分析多个项目时，每个分项目报告都要写对应地址；汇总报告还必须提供“项目 / GitHub 地址”对照表。
- 若仓库确实没有可核验的 GitHub 地址，应明确写成 `项目地址：未发现可核验的 GitHub 地址`，不得省略这一项或伪造链接。

## 交付要求

- 报告范围与用户请求一致；初步了解、单个能力和各类深入分析分别采用对应的呈现要求，不将框架对象格式套用于策略文件。
- 对象职责、内部子项、功能关系、流程、接口和生命周期相互一致；同一对象使用同一名字，事实有依据，未确认项明确标出。
- 名词表简要解释报告使用的项目专有名字和概念，对象的结构与操作留在对应章节，避免重复。
- 每份项目报告开头写明对应的项目地址，注明分析基线与证据边界；深入分析首章明确选定代码范围，后续章节不越界。
- 每部分内容与全文的范围、术语、对象和流程相符；新增关键对象、专有名字或范围变更时同步回填前文，不到末尾才处理冲突。
- 产物遵循用户指定路径、格式和范围；未指定时采用本 skill 的默认目录与 Markdown 约定。
