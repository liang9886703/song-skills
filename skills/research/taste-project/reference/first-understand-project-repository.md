# 初识项目仓库

面向具有计算机和软件开发通用知识、但不了解本领域专有名词的产品经理，按以下结构介绍项目仓库。报告内容以可核验信息为依据，补全主语并梳理逻辑，不添加未经支持的含义。

## 语言风格

- 少用专门名词，只有没有合适的替代名词时才用专业名词；能用大白话就用大白话。大白话指的是计算机专业的普通从业者能听懂的说法，比如进程/线程/agent/幂等/鉴权，就是普通名词；坏的例子是"exactly-once 语义边界"这种只有特定领域才用的说法。
- 讲解机制时不能说函数名/变量名/文件名/代码路径，重点说"干了什么"，而不是"哪个函数调了哪个函数"。
- 正确：启动 opencode server 并读取 stdout 输出解析得到 url。
- 错误：createOpencodeServer 用 cross-spawn 启动 opencode serve，默认 127.0.0.1:4096，并设置 OPENCODE_CONFIG_CONTENT，证据 packages/sdk/js/src/server.ts:22-40。它读取 stdout 的 opencode server listening 行解析 URL，证据 :43-70；超时、exit、error 会 reject，证据 :75-91。

报告正文开头必须先写 `项目地址：<GitHub URL>`。项目地址必须有可核验的仓库信息支持，例如用户提供的链接或 Git remote，不能凭项目名猜测；若无法核验，明确写 `项目地址：未发现可核验的 GitHub 地址`。

下列各部分均属于必须说明的内容。除这些部分外，如有任何能帮助读者熟悉项目的信息，可以在文末新增标题补充。

## 背景

说明项目属于哪个领域，例如 agent runtime、agent 基础设施等。

## 解决的问题

说明项目解决什么问题，并把背景说清楚：如果没有这个项目，会出现什么问题。

## 名词表

面向不懂这个项目的科班计算机中级工程师来写，本文出现的所有项目级名词/概念/定义都必须在这里有过解释。

表应该包含 | 通用名词 | 本仓库的叫法 | 解释 |。
统一名词：名词表中不能重复同一个概念，也不能让同一个概念出现两个名字；如果原文有两个名字，用 name1/name2 写在同一行。
充分的解释：每个解释都必须包含完整的主语、谓语和宾语，用大白话解释，不使用专业术语。

## 贡献的场景

说明项目包含几个部分。一个仓库通常可能有多个版本、多个服务和多种打开方式，例如 wrap 服务、本地终端、本地 agent、本地连接云端服务器、云端 agent。

## 用户故事

把项目当作用户可以直接使用的产品，描述部署后用户会如何使用它。这里的用户也包括程序员；例如，程序员可以先做什么、再做什么，从而实现什么。这里写故事，不写具体执行命令。

## 如何跑起来

只说明项目属于哪种运行方式，不说明如何部署。例如：本地可以轻量级部署但依赖 NVIDIA 显卡、必须部署在 Kubernetes 集群中、不能单独部署、必须通过写代码调用。

## 整体链路

整体链路以 Markdown 可展示或嵌入的图为主、文字为补充，具体绘图工具由 Agent 选择。模块、组合和包含关系、请求流转等可以写进图中的信息，都应写进图中。

### 服务一

说明项目由哪些模块构成、这些模块之间的组合和包含关系，以及这些模块如何配合构建请求链路。

## 仓库信息

### 仓库结构

按仓库原有目录结构展示与主线功能相关的部分，例如：

```text
runner-famou-ts/
├── index.ts                         # 进程入口
├── config/                          # 服务配置
├── core/                            # Runner 核心生产代码
│   ├── kernel/                      # 最底层运行契约
│   ├── runner/                      # 会话编排引擎
│   │   ├── runner.ts                # 正式服务的入口
│   ├── router/                      # 网络和协议入口
│   ├── agents/                      # 具体 coding agent 适配层
│   │   ├── agents.ts                # 抽象的 agent 接口
│   │   ├── opencode/                # 封装 opencode 为一个可交互的模块
│   └── modules/                     # 封装各种基础能力
│       ├── controller/              # 管理 agent 进程
│       ├── event-delivery/          # 将 agent 输出的事件流发送到远端消息队列
│       ├── event-intervent/         # 修改 agent 输出的事件流
├── .agents/
│   ├── references/                  # 项目文档
│   └── skills/                      # 项目专用 Agent skills
```

注意详略得当：不必说明每个项目都有的测试和工具，也不必罗列与主线功能无关的零碎组件；只说明前面提到的功能相关部分。

### 依赖

说明项目是否依赖需要通过网络请求的第三方服务，以及是否能独立运行。说明项目封装了哪些服务、项目基于哪些服务开发；这里重点说明业务逻辑重度依赖的主体部分，不必说明工具包。例如，openclaw 基于 pi agent 开发，同时底层也支持 codex、claude code 等其他 agent。

### 技术栈

说明项目的不同部分分别使用什么语言和框架。

### 仓库元信息

说明仓库的 star 数量、近期活跃度和创建时长。

## 仓库完成度

机制说明讲清楚行为，具体代码位置、测试和 PR 链接放在证据列或段落末尾。

判断文档说明的能力在当前代码中完成到了哪一步。报告注明分析日期、分支或提交、影响分析的未提交改动，以及结论覆盖的能力和运行环境；区分当前默认产品、可选特性和未来设计目标。

### 核验与输出

- 按用户能观察到的能力，对照 README/设计说明、真实调用入口、实现和测试。重点核查入口是否接通、默认构建是否包含功能，以及平台或配置条件；接口存在、只打印计划、模拟返回都不能等同于实际执行。
- 用表格呈现：`| 能力 / 场景 | 文档声明 | 实际实现 | 验证证据 | 完成度与缺口 |`。完成度使用“主体完成 / 部分完成 / 未实现”；无法确认时写“证据不足”，不把“本次没测”当作“没有实现”。已明确标为未来目标的项目，要标注其规划性质。
- 区分源码判断、已有测试内容、本次实际测试、目标环境端到端验证和 CI 结果。不要把测试名称、测试数量或 CI 绿灯当作真实用户链路已通过；检查关键测试是否只覆盖参数、模拟服务或因环境条件跳过。
- 报告注明已有验证的范围、条件、结果和未确认项；验证方式由 Agent 按任务决定。没有验证结果时不推断功能不存在，也不把未经验证的行为写成已确认。
- 总结功能实现、产品接通和部署验证三个方面的完成程度，列出影响使用的主要缺口。没有清晰验收清单和计算口径时，不给伪精确的整体百分比；若评分，说明分母、权重和不确定性。

更新已有报告时，注明新旧基线，将变化结论分成“新增 / 已解决 / 仍存在 / 未重新验证”，避免把旧测试结果写成本次新结果。

## 近期迭代方向（最近 10 个 PR 与近一个月取较少）

目的不是复述提交标题，而是说明维护者最近在推进什么，以及这些变化如何影响当前能力和完成度。

### 取样口径

- 默认比较“最近 10 个已合并 PR”和“近一个月内合入默认分支的 PR”，**取 PR 数量较少的范围**；等价于按合并时间倒序，最多取近一个月内的 10 个 PR，并分析其实际合入的代码。近一个月以查询时点向前回溯一个月，报告写明起止日期、时区、目标分支和实际样本数量。用户指定其他范围时按其要求执行。不要用最近更新时间或 PR 编号代替合并时间。
- 例如：近一个月有 6 个 PR，就分析这 6 个；有 25 个，就分析最近 10 个；没有已合并 PR，就说明该时间窗口没有 PR 样本，不向更早历史补足。
- PR 样本须有真实来源和可核验链接，不限定获取工具。GitLab MR、iCode CR 等保留原平台名称，不伪称 GitHub PR。
- 默认不混入未合并、已关闭未合并的 PR；若它们能解释下一步方向，可在样本之外单独说明“进行中/尚未落地”。自动依赖更新、文档 PR 也保留在样本内，并按实际影响分类。
- 权限不足、平台无 PR 或仅能取得本地历史时，明确说明限制；可分析近一个月内的提交代码作为补充线索，但必须标为“提交历史替代分析”，说明提交数量、时间口径及无法核验 PR 数量。不得把 commit 数量当作 PR 数量，也不得据此认定仓库没有 PR。

### 分析与输出

- 每个样本的变化结论应有正文、实际改动或其他足够证据；只有标题或元数据时明确限制置信度。
- 提供样本表：`| PR / MR / CR 链接 | 合并日期 | 主要改动 | 方向分类 | 对能力的影响 |`，让读者能核对所用样本。
- 按证据归纳迭代方向，例如新能力、补齐已有链路、稳定性/安全修复、性能、接口或架构调整、工程与文档维护。提供方向表：`| 迭代方向 | 对应 PR 与数量 | 解决的问题 | 对完成度的影响 |`。同一 PR 若归多个方向，说明数量允许重叠，不把重叠计数当作总 PR 数。
- 结合样本覆盖时间说明主要投入方向及典型变化，不从少数 PR 推断长期路线图。区分实际合入的行为、仅增加测试或文档、以及仍属计划的内容；合并不代表已发布，也不代表已包含在当前分析的本地提交中，应核查版本关系或明确尚未核验。
