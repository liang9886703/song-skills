> 晨报每篇 md 的写法约束。单独用也成立。

## 干什么

把一篇文章的主干保留下来、按可读的结构重新排版。**不是重写一篇总结报告**。读者读完应该知道这文章在讲什么、值不值得细看、主干是什么，而不是读到另一篇文章。

## 开头：导读

必须有。一到两句，说清两件事：

- **这篇文章在讨论什么话题**（不是「本文介绍了…」，是具体话题，比如「monorepo 下 agent 批量推送的 git 后端怎么做」）
- 作者的姿态：提出一个观点 / 给出一个结论及推导 / 给出一套可执行的工作流

导读就是判断「值不值得读」的依据，不要拿它复述正文。

## 正文：命中框架，不凑框架

先看文章里**实际有什么**，只写命中的那几条：

| 框架项 | 文章里有才写 |
| --- | --- |
| 背景 / 过去怎么做 | 作者自己交代了旧做法或旧处境 |
| 要解决的问题 | 作者明说卡在哪、不解决会怎样 |
| 核心主张 | 一句能被反驳的断言 |
| 推导 / 证据 | 给出的论证链条、数据、实验条件 |
| 机制 / 工作流 | 分步展开的做法、每个环节的输入输出 |
| 局限 | 作者自己承认的局限 |

规则：

1. **没有的章节不要创建**。文章没提背景就不写背景段，不联网去查、不自己补历史、不引入原文以外的信息。
2. **假设读者知道背景**。看不懂这篇的人在读者列表外；不要用篇幅去解释常识。
3. **略去细节，保留主干**。文章用十个例子证明一个观点，总结写观点和例子在证明什么，不逐个重写例子；给了一套工作流，写清步骤和每步干什么，不抄操作细节。
4. **不能命中框架的内容单独起标题**。文章主干里如果有框架盖不住的部分（一个反直觉的观察、一段历史、一个工具选型），给它自己的小标题，不要硬塞进上面任何一个。
5. 不替作者补他没写的评价。文章没说的代价、没讨论的边界，不写。

## 标题：优先用原文的

- 文章本身结构好、标题有逻辑有观点：**直接用它的标题**，只做层级整理。
- 标题混乱、几乎没有标题、或标题空泛套话：按上面命中的框架重建，用文章自己的术语。
- **不确定就用原文的标题**。

不造作者没说过的小标题，不把作者的一段拆成三段并自己起名。

## 长短

跟着原文走，不设固定字数。一篇文章只讲一个观点，两三百字就够；一篇长文有推导有工作流，一千字也正常。判断标准是：主干是否完整，细节是否已经去掉。HF 论文这种只有一句结论的，写清结论、它怎么验证的就停。

## 自检

1. 导读能不能让人判断值不值得看，而不是读完才发现内容不在导读里？
2. 每一个小标题，是我自己发明的，还是文章里有的？发明的那个是否真的不属于任何已有章节？
3. 有没有哪一段是文章没有的、我补充的？（有就删）
4. 有没有把作者的一个例子完整复述了一遍而不是写它在证明什么？
5. 有没有为了凑齐框架而写了一节其实文章里没有的内容？
6. 全文的主干能不能一句话说出来？说不出来说明被细节淹了。

## 例子（构造示例，非真实文章）

> ## 导读
> 作者在讨论 agent 工具调用的预算控制，主张把「一个总预算」换成按阶段分的预算树，理由是总额度会让前期步骤饿死后期步骤。
>
> ## 旧做法不够用的地方
> 普遍做法是整个会话一个总超时，超时杀进程。这在单步任务上够用，但任务一旦分成成本差异很大的几个阶段就失效：搜索阶段吃掉大部分额度，验证阶段没有剩余，任务以部分完成结束，日志里看起来像模型放弃。
>
> ## 预算树
> 调用方发起任务时声明阶段划分，每段独立额度，不自动流转；跨阶段借用要模型显式调一次 `borrow` 并说明理由；额度耗尽不抛异常，返回已完成部分和阶段名加原因码，调用方据此决定重试还是降级。
>
> ## 证据与条件
> 原文在 40 个多阶段任务上对比单总额度与分层额度：完整完成率 22/40 → 31/40，平均调用次数反而降了约 12%。条件是同一模型、作者自己的任务集，未公开 benchmark 验证。

注意这个例子：三节全部来自文章实际说的内容，没有硬造一个「背景」段去讲行业史，也没有替作者补他没写的代价。
