# Shell 脚本编写规范

本规范覆盖日常 Shell 脚本，以及测试、恢复、E2E、harness、服务启停类脚本。

规范使用以下级别：

- **必须**：已有规范或对话中反复明确的硬约束。
- **推荐**：为可维护性、可诊断性和安全性补充的工程建议。
- **可选**：仅在场景需要时使用。

## 1. 总体原则

1. **必须可重复运行**：上一次运行遗留的目录、日志、PID、端口、socket、store、DB 或临时配置，不能影响本次结果。
2. **必须失败即停**：测试脚本用于暴露问题，不应吞掉错误后继续制造无效结果。
3. **必须函数化组织**：运行步骤全部封装成函数，由 `main` 串联；全局只放常量、路径和简单 helper。
4. **必须保留证据**：重要输入、输出、请求、响应、中间结果、子进程日志和失败现场必须落盘，不能只显示在终端。
5. **一个任务一个输出根目录**：所有子步骤、子脚本和子进程的产物都归入同一任务目录，再按用途分子目录。
6. **成功和失败路径都要覆盖**：只有模拟失败而没有正常完整路径，不算完成测试覆盖。

## 2. 解释器与严格模式

### 2.1 明确选择 Shell

- 使用 Bash 特性（数组、`[[ ]]`、`local`、进程替换等）时：

  ```bash
  #!/usr/bin/env bash
  ```

- 需要 POSIX `sh` 兼容时：

  ```sh
  #!/bin/sh
  ```

不要写着 `#!/bin/sh`，实际却依赖 Bash 语法。

### 2.2 默认严格模式

通用硬规则是：

```sh
set -eu
```

Bash 脚本中，只要管道任一步失败都应使整条命令失败，再增加：

```bash
set -o pipefail
```

注意：`pipefail` 不是 POSIX `sh` 标准能力。使用它就应明确选择 Bash，或先确认目标 `sh` 支持。

### 2.3 不要滥用错误豁免

- 不要在主流程使用大段 `set +e`。
- 不要用无说明的 `|| true` 吞错。
- 允许在清理、探活、检查“预期失败”时局部忽略退出码，但必须限定范围并说明原因。
- 需要检查退出码时，应显式进入条件分支，例如 `if command; then ... else ... fi`。

## 3. 脚本头部说明

脚本最前面必须包含以下四项：

1. **Usage**：运行方式、参数、必要环境或前置依赖。
2. **Principle**：脚本测什么、如何验证、成功标准是什么。
3. **Main flow**：只列主流程函数调用图，不展开实现细节。
4. **Output files**：输出目录、主要文件及各自用途。

示例：

```bash
#!/usr/bin/env bash
#
# Usage:
#   bash scripts/example_e2e.sh [--keep-runtime]
#
# Principle:
#   启动被测服务，经真实网络入口完成一轮请求，断言响应和持久化结果。
#
# Main flow:
#   main
#   ├── parse_args
#   ├── validate_config
#   ├── init_environment
#   ├── start_services
#   ├── run_case
#   └── print_summary
#
# Output files:
#   test_out/example/logs/main.log       主流程日志
#   test_out/example/logs/server.log     服务日志
#   test_out/example/http/               HTTP 请求与响应
#   test_out/example/debug/failure.txt   失败摘要
```

注释应解释结构、意图、边界和不明显的原因，不要逐行翻译代码。

## 4. 文件组织顺序

脚本按以下顺序组织：

1. 头部说明
2. 严格模式
3. 静态配置
4. 输出目录和输出文件定义
5. 通用 helper
6. 参数解析与配置校验
7. 环境初始化和退出清理
8. 各步骤函数
9. `main`
10. `main "$@"`

除 `main "$@"` 外，不在全局直接启动服务、创建目录、发请求或执行测试步骤。

主入口保持清楚：

```bash
main() {
  parse_args "$@"
  validate_config
  init_environment
  start_services
  run_case
  print_summary
}

main "$@"
```

聚合脚本应是薄调度器，只负责解析参数、选择子任务、调用子脚本并输出汇总；复杂业务逻辑放在对应子脚本或函数中。

## 5. 配置与环境变量

### 5.1 少用启动环境变量

- 大多数稳定配置直接定义在脚本顶部。
- 环境变量主要用于凭据、环境差异、CI 注入或确实需要覆盖的参数。
- 同一配置只能有一个明确的解析入口，不要在多个函数中重复拼默认值。
- 启动任何进程前完成配置校验，包括路径、端口、超时、枚举值和依赖命令。

### 5.2 共享环境文件必须纯净

专门用于 `source` 的 `runner-env.sh` 一类文件，只放可重复执行的环境定义：

```sh
export SERVICE_PORT="${SERVICE_PORT:-18090}"
export LOG_LEVEL="${LOG_LEVEL:-debug}"
```

不要在这类文件中执行：

- `mkdir`、`rm`、`cd`
- `trap`
- FIFO/socket 初始化
- 进程启动或停止
- 网络请求

这些有副作用的操作由调用方负责。

### 5.3 凭据处理

- 不把密钥写入脚本、命令输出、日志或失败快照。
- 不为读取少量凭据而直接 `source` 整份不受信任配置文件；应只解析需要的键。
- 日志只记录凭据状态，例如 `<set>` / `<unset>`。
- 不需要凭据的子进程应显式剥离相关环境变量。
- 运行生成的敏感配置应使用严格权限，并在退出时删除。

## 6. 变量、参数与命令写法

### 6.1 引用变量

- 默认写 `"$var"` 或 `"${var}"`，避免空格和通配符展开。
- 路径、URL、请求体、用户输入和命令参数必须引用。
- 使用 `--` 分隔选项和路径，例如 `rm -rf -- "$target"`。
- Bash 中复杂命令参数优先用数组，不把整条命令拼成一个字符串后交给 `eval`。
- 禁止用 `eval` 处理用户或外部输入。

### 6.2 多行处理

多行输出优先先进入变量或文件，再做解析：

```bash
response="$(curl -sS --fail-with-body "$url")"
printf '%s\n' "$response" >"$HTTP_DIR/response.json"
status="$(printf '%s\n' "$response" | jq -r '.status')"
```

不要把获取、过滤、转换、断言和写文件全部塞进一条很长的裸管道。长管道会隐藏失败位置，也不利于保留中间证据。

如果结果较大、包含二进制内容或需要多次使用，直接落到文件，不要长期保存在变量中。

### 6.3 函数与局部状态

- 一个步骤一个函数，函数名表达动作，例如 `validate_config`、`start_server`、`wait_until_ready`。
- Bash 函数内部变量优先声明为 `local`。
- 函数通过退出码表达成功或失败；结构化结果通过 stdout 或明确文件返回。
- stdout 若作为函数返回值，就不要混入调试日志；日志写 stderr 或日志文件。
- 不依赖隐式全局变量在多个函数间传递复杂状态。

## 7. 环境初始化与可重复运行

运行前必须完成：

- 校验配置和依赖命令。
- 校验将要清理的路径，拒绝空路径、根目录、用户目录和过宽目录。
- 清理旧输出目录并重建目录结构。
- 清空或重建日志文件。
- 清理当前任务拥有的旧 PID、端口、socket、store、DB 和临时配置。
- 记录本次运行配置；敏感值只记录是否设置。

不要通过宽泛的进程名批量杀进程。优先保存本次启动的 PID，并只清理这些 PID。清理旧端口时也应先确认占用者和任务归属。

临时目录优先用 `mktemp -d` 创建。需要保留证据时，再把明确的结果复制到任务输出目录。

## 8. 输出目录

同一个任务只使用一个输出根目录。推荐结构：

```text
test_out/<task-id>/
  config/
    run.env.redacted
  logs/
    main.log
    server.log
    runner.log
  http/
    request-001.json
    response-001.headers
    response-001.body
    response-001.meta
  turns/
    round1/
      request.json
      events.jsonl
      answer.txt
    round2/
      ...
  debug/
    poll-trace.log
    failure.txt
    process-snapshot.txt
```

目录职责：

- `config/`：脱敏后的本次运行配置。
- `logs/`：主脚本及所有子进程日志。
- `http/`：请求、响应头、响应体和请求元信息。
- `turns/`：逐轮输入、事件、回答和断言结果。
- `debug/`：dump、轮询轨迹、失败快照和诊断现场。

子脚本不能各自在仓库不同位置散落输出；它们应接收或继承任务级输出根目录，在其下创建自己的子目录。

## 9. 日志与证据

### 9.1 最低日志集合

测试、恢复和 E2E 脚本至少保留：

- 主流程日志
- 每个子进程日志
- 请求日志和响应日志
- 每轮请求文件和回答文件
- 每轮 debug dump
- 失败快照

HTTP 证据至少包含：

- 时间
- 方法
- URL
- 请求体或请求文件
- 响应状态码
- 响应头
- 响应体
- 客户端退出码

### 9.2 日志格式

推荐每行包含：

```text
2026-07-22T15:04:05+0800 level=INFO step=start_server message="server started" pid=12345
```

终端只输出关键进度和最终摘要，完整细节写入文件。子进程 stdout/stderr 要有独立日志，不要全部混入主日志。

断言失败时，先保存现场，再返回非零退出码。失败快照至少说明：失败步骤、预期、实际、相关文件路径和子进程状态。

## 10. 后台进程、等待与清理

只要启动后台进程，就必须配置 `trap` 做退出清理。

要求：

- 保存每个后台进程的 PID。
- 清理函数可以重复调用，不因进程已经退出而失败。
- 保留脚本原始退出码，不能让清理失败覆盖真正失败原因。
- 清理顺序与启动顺序相反。
- 先请求正常退出，必要时再升级终止方式。
- 清理本次生成的 socket、FIFO、临时配置和敏感文件。
- 退出前确认关键端口、进程和临时资源已经释放。

等待服务就绪时使用带超时的 readiness probe，不用固定长 `sleep` 猜测服务是否启动完成。轮询过程写入 `debug/poll-trace.log`。

## 11. 失败与断言

- 首个非预期错误立即停止主流程。
- 每个关键步骤都应有明确的成功判据，不能只凭“命令执行过”。
- 预期失败场景要同时断言退出码、错误内容和状态未被污染。
- 正常场景要覆盖从输入到最终外部结果的完整路径，不能只证明请求被接收。
- 后台进程失败必须能传回主脚本；不能让主脚本继续等待直到超时才发现。
- 超时错误要打印正在等待的条件，而不是只写“timeout”。

## 12. 安全约束

- 删除前对目标路径做白名单或前缀校验，禁止对空变量、`/`、`~`、`$HOME` 或仓库根目录做递归删除。
- 不把外部输入直接拼接进 Shell 命令。
- 不解析 `ls` 输出；遍历文件使用 glob、`find -print0` 或 Bash 数组。
- 不把密钥放在命令行参数中，避免出现在进程列表。
- 下载或执行外部内容时要校验来源；不要 `curl ... | sh`。
- 生成敏感文件时推荐先设置 `umask 077`。
- 失败快照和 debug dump 同样必须脱敏。

## 13. 完成前检查清单

### 结构

- [ ] 头部包含 Usage、Principle、Main flow、Output files。
- [ ] 静态配置、输出路径、helper、初始化、步骤、`main` 顺序清楚。
- [ ] 运行步骤都在函数中，全局没有隐藏副作用。
- [ ] 聚合脚本保持薄，只负责调度和汇总。

### 可重复运行

- [ ] 启动前校验配置和依赖。
- [ ] 旧输出和本任务残留资源得到安全清理。
- [ ] 输出目录统一，子步骤不向别处散落文件。
- [ ] 连续运行两次结果一致，不受上次运行污染。

### 错误与清理

- [ ] 默认启用 `set -eu`；Bash 管道按需启用 `pipefail`。
- [ ] 非预期错误会立即停止。
- [ ] 没有无说明的 `|| true` 或大段 `set +e`。
- [ ] 后台进程有 PID 管理和 `trap` 清理。
- [ ] 失败时保留原始退出码和失败现场。

### 日志与安全

- [ ] 主流程、子进程、请求、响应和逐轮结果均落盘。
- [ ] HTTP 日志包含状态码、响应头、响应体和客户端退出码。
- [ ] 凭据不出现在日志、参数、快照和子进程环境中。
- [ ] 递归删除目标经过安全校验。

### 验证

- [ ] POSIX 脚本执行 `sh -n <script>`。
- [ ] Bash 脚本执行 `bash -n <script>`。
- [ ] 推荐执行 `shellcheck <script>`。
- [ ] 推荐执行 `shfmt -d <script>` 或项目已有格式检查。
- [ ] 正常路径和关键失败路径均有测试。
- [ ] 目标测试通过后，再按风险运行相邻测试或更高层验证。
