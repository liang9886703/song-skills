# daily-report-writer

## 工作流

1. 确定日报日期。除非用户指定日期，否则按用户本地时间判断：每天的日报窗口是当天 08:00 到第二天 08:00；如果当前时间早于 08:00，仍归入前一天日报。
2. 使用 `scripts/prepare_daily_context.py` 创建/读取当天日报文件 `~/daily/YYYY/MM/DD.md`，并读取最近 3 个有效日报文件（包括今天）。有效日报指已经存在的日期 Markdown 文件；中间缺失的日期可能是非工作日。
3. 默认调用 `scripts/collect_agent_context.py --date YYYY-MM-DD` 读取目标日报窗口内的 Codex、Claude Code、OpenCode 三类 coding agent 会话记录；如果脚本不可用或某类日志不可访问，再手工读取当前线程、相关终端输出，以及环境可访问的会话日志。重点关注用户的提问，以及后续发生的动作。
4. 按「意图/目的、动作、操作对象、结果、时间」提取工作项。通用技术学习不写，除非它直接服务于某个具体工作项。
5. 如果 `assets/templates/daily-report.md` 存在且不是占位文件，优先参考该模板组织结构；如果不存在，沿用当天日报已有格式或使用下方建议格式。
6. 将工作项去重并有机整合进今天的日报。保留已有内容，补充不完整项目，不要重复添加含义相同的条目。
7. 保存更新后的日报文件。

## 日期与路径

日报路径固定为：

```text
~/daily/YYYY/MM/DD.md
```

例如，`2026-06-09` 对应 `~/daily/2026/06/09.md`，覆盖的工作时间是 `2026-06-09 08:00` 到 `2026-06-10 08:00`。

整理会话时要显式关注时间：

- 只纳入目标日报窗口内的工作。
- 00:00-07:59 发生的工作属于前一天日报。
- 如果会话没有精确时间，但上下文显示属于今天的工作，可以谨慎纳入，并用概括表述。
- 日报正文可以在标题或开头标记时间窗口，例如 `# 2026-06-09 日报（08:00-次日 08:00）`；若已有格式不同，优先沿用已有格式并补充时间信息。

## 上下文脚本

在本 skill 目录下运行：

```bash
python3 scripts/prepare_daily_context.py --create-today
```

常用参数：

- `--date YYYY-MM-DD`：指定日报日期；未指定时按 08:00 边界自动推导。
- `--daily-root PATH`：覆盖默认日报根目录 `~/daily`。
- `--days N`：读取最近 N 个有效日报，默认 `3`。
- `--no-content`：只列路径，不输出文件内容。

脚本会输出 JSON，包含目标日报日期、时间窗口、今天文件路径、是否新建，以及最近有效日报内容。脚本只负责收集上下文，最终取舍和润色仍要由 Codex 判断。

## Agent 会话脚本

写日报时默认运行：

```bash
python3 scripts/collect_agent_context.py --date YYYY-MM-DD
```

如果用户未指定日期，可以不传 `--date`，脚本会按本地时间和 08:00 边界自动推导目标日报日。该脚本会读取并压缩以下三类会话记录：

- Codex：`~/.codex/sessions/YYYY/MM/DD/*.jsonl`
- Claude Code：`~/.claude/projects/**/*.jsonl`
- OpenCode：`~/.local/share/opencode/opencode.db`

脚本输出 Markdown 摘要，按来源和会话列出用户目标、关键消息和最后产出。输出仍只是素材，必须继续人工判断：

- 只纳入目标日报窗口内的工作。
- 忽略系统提示、权限审批、工具流水、纯测试回复和无业务意义的闲聊。
- 同一工作在 Codex、Claude Code、OpenCode 中重复出现时，要合并成一个工作项。
- 输出过长时，优先按项目、问题、结果聚合，不要把对话流水直接写进日报。
- 脚本失败或缺少某类日志时，不阻塞日报生成；记录已成功读取的来源，并用当前线程和可访问日志兜底。

## 模板位置

预留模板路径：

```text
assets/templates/daily-report.md
```

当前可以没有模板。以后如果该文件存在，先读取模板并按模板结构写日报；如果模板不存在或只是占位文件，不要自行创建模板内容，继续使用当天已有格式或建议格式。

## 写作规则

- 全文用中文写。
- 按需要组织为：调研、提效、开发、线上维护、其他。
- 不写纯「学习」项；只有当学习直接支撑了某个具体工作，才融入对应工作项。
- 不出现具体代码、变量、实现细节、分支名、文件名或文件路径。
- 可以出现项目、仓库、产品、平台或软件名称，前提是同事能据此理解工作范围。
- 按「为什么/做了什么/对象是什么/结果如何」描述，必要时补充大致时间段。
- 线上维护只写已知环节：问题现象、分析判断、方案设计、实现处理、验证、上线、后续跟进。不要脑补未知环节。
- 保持同事可读，避免聊天记录口吻，例如不要写「用户让我」「我帮忙」。
- 强去重：如果今天已有相同工作，原地补充结果或背景，不新增重复条目。
- 结果不明确时，使用谨慎表述，例如「推进中」「完成初步验证」「形成方案」「待继续跟进」。
- 生成周报或总结时，不要默认添加「下周关注」「下周安排」「后续计划」等未来计划章节；只有用户明确要求时才写。
- 生成周报或总结时，优先使用「几个字短标题 + 冒号 + 子 bullet 详述」的层级结构；同一主题的事项要合并到一个短标题下展开，不要拆成多个并列一级 bullet。
- 周报或总结的一级 bullet 应表达主题归类，例如「计费安全」「事件可靠性」「模块框架」「外部访问」「调研归档」；具体动作、判断、结果放到该主题下的子 bullet 中。

## 建议格式

优先沿用当天日报已有格式。如果文件为空，可以使用：

```markdown
# YYYY-MM-DD 日报（08:00-次日 08:00）

## 开发

- ...

## 提效

- ...
```

省略空章节。
