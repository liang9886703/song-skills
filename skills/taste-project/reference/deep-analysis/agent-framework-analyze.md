Agent 框架深入分析

适用条件：仓库属于 Agent 框架类型，且用户明确要求深入分析整个项目。初步了解项目或分析单个能力时，按主流程使用对应约束。

面向具有计算机和软件开发通用知识、但不了解本项目的产品经理和中级工程师，分析 Agent 框架如何围绕一个会话组织数据、处理用户请求，以及向外提供能力。

分析方式：只读目标仓库源码及理解代码必需的配置和说明，不运行测试、构建、基准或探针，不启动服务，也不为分析安装运行依赖。报告只呈现源码能支持的机制与结论，不写测试命令、执行结果、通过率、控制台输出或测试输出附录。

重点回答五个问题：关键数据对象是什么，它们如何关联与协作，一次新会话请求如何推动这些对象变化，对外接口分别对哪些对象做什么，以及这些能力在代码目录和文件中如何组织。按下面的结构产出报告，不要把报告写成代码调用清单。

分析方法：多轮回看对象

对象职责需要在完整链路中反复核对，不能看到一个定义、一个方法或一处调用就定论。分析过程中维护同一份对象清单，将新发现回填到已有介绍中，而不是让前后的描述各自成立、互相矛盾。

1. 初次阅读对象时，记录它的代码名字、主要数据、初步职责和待确认问题。结合定义、创建位置和主要使用方形成暂定判断，区分“对象本身承担的职责”和“调用方借助它完成的业务”。
2. 梳理数据流时，逐个回看涉及的对象：谁创建或取得它、谁修改它、谁读取其结果，以及何时保存、恢复或释放。发现首次判断只覆盖某个阶段或某个分支时，补全职责，或明确结论的适用范围。
3. 梳理接口和对象关系后，再回看清单中的每个对象，核对它在不同入口、主要分支和生命周期阶段的作用。对于尚未在链路中找到的对象，继续确认它是否实际使用、属于其他场景，或仅为未接通的设计；不能只因没有出现在主线中就认定它没有职责。
4. 任务交付前，整体再过一遍对象清单、对象关系、主体对话数据流、接口语义和代码文件结构，并逐对象回查相关实现。核对职责是否完整、分类和层级是否合理、数据归属与生命周期是否一致，以及报告中的每项职责是否有实际使用证据。发现遗漏或冲突时，修正所有受影响的章节；无法确认的部分保留为未确认项，不作确定结论。

每次回看都应结合新获得的上下文检查相关源码，而不是只重读对象定义或润色已有说明。对复杂对象重点核查主要创建方、读写方、调用方及收尾逻辑；对简单对象可简要核对，但不能在最终复核中遗漏。

语言风格

少用项目专有术语，用通用计算机知识解释系统行为。

### 1. 对象介绍

在数据对象章节首次展开介绍对象时，单独开一段介绍，以“代码中的名字（通用语义：xxx）”为标题，保留它在本仓库中的真实叫法。

每个展开介绍的对象都优先使用精简的实际代码定义，并在关键字段或接口旁写业务职责注释；必要时用结构伪代码简化表达。这一要求适用于 SessionRecord、SessionSpec 等所有对象。用字段直接展示对象包含、持有或引用的主要组件和数据，在对象或字段旁用注释解释系统职责、业务含义和相互关系，优先于用一段文字枚举“持有什么”。

每个代码对象的定义前，必须用独立注释行标注真实定义文件，格式为 `// 仓库相对路径/xx.go`，不写行号或行号范围。同一代码块包含多个对象时，每个定义都单独标注；它们来自不同文件时分别写各自路径。路径必须从源码核验，不能仅依据对象名猜测。其他语言采用对应语言的注释语法。

保留本仓库真实的对象名、关键字段名和相关对象名。可直接摘录实际结构或接口并删去非关键部分；如改写为伪代码，应标明精简或操作示意，不能把示意字段或接口写成真实定义。只列主要业务组件、业务数据及理解它们所必需的配置、标识和状态；用省略号略去其余部分，不照抄完整结构，也不展开锁、通道、定时器等程序控制细节。注释必须解释业务作用，不能只把字段名或类型名翻译成中文。

复杂对象的结构、主要成员和业务数据统一通过代码及注释展示。伪代码难以表达的生命周期、持久化边界、特殊分支，以及缺少对象会失去的能力，再用少量文字补充；不要在代码后逐字段重复解释。不要只罗列字段类型、继承关系或方法签名而没有职责说明。

正确示例：

#### Session（通用语义：持续对话的内存协调对象）

```go
// Session 在内存中协调一条持续对话的成员、配置和执行资源。
// 仅保留关键业务字段；省略锁、通道、执行槽等程序控制细节。
// runtime/agentway/runtime.go
type Session struct {
    memberReleases map[AgentID]*memberRelease // 跟踪本会话成员的退出与资源释放，失败时可重试
    rt             *LocalRuntime             // 引用当前 Host 的共享内核，取得存储、运行对象和远端调用能力
    id             SessionID                 // 将本会话的输入、成员、事件历史和后续请求关联起来
    revision       uint64                    // 对应持久会话记录的修订信息
    spec           SessionSpec               // 保存实际生效的会话配置、位置绑定和 Agent 恢复描述
    agents         map[string]Agent          // 按 AgentID 持有已接纳的活跃 Agent 句柄
    members        []Member                  // 记录已加入的 Agent 或人类成员；成员身份与 Agent 句柄分开
    channels       map[ChannelID]*liveChannel // 持有已打开的外部消息渠道，接收输入并投递输出
    proxy          SessionDelegate           // 整条会话委托到远端时，转发会话操作
    peerAgents     map[string]Agent          // 持有位于其他 Host 的会话成员 Agent
    // ……
}
```

错误：`Session` 是一个包含若干字段的类；入口调用 `getSession()`，然后执行 `sandboxManager.get()`。

### 2. 数据流介绍

每段流程伪代码开头，用一行注释写承担该流程主要编排或实现职责的文件，例如 `// 仓库相对路径/main_flow.go`，不写行号。一段流程只标一个主要文件，不罗列沿途调用文件；应核实主要文件确实承载该流程。

数据流优先用伪代码表达，把输入、对象获取或创建、数据变化、持久化、输出及结束条件直接写成顺序步骤。使用赋值、条件、循环、等待和后台执行标明关系，注释说明业务目的；文字只补充伪代码难以表达的边界。

以“获取什么、产生什么、修改什么、保存什么、发出什么”为主要动作，使用前文统一的对象名字。中文动作可以概括业务步骤，但应标明是流程伪代码，不能伪装成仓库中真实存在的函数。保持实际先后顺序和分支，不逐行翻译调用栈，也不把异步接纳写成同步执行完成。

例如：

```text
// path/to/main_flow.go（示例路径，实际报告应填写核验后的主要文件）
Session = 按会话标识获取或创建会话
Sandbox = 通过沙箱控制组件获取或新建执行环境
将 Sandbox 的身份关联到 Session

for 本轮执行产生的输出:
    Event = 将输出转换为会话事件
    等待事件保存成功
    向调用方发出 Event

保存本轮结果及恢复信息
结束本轮输出流 // 会话是否继续保留，按真实实现说明
```

上述名字只是表达方式示例，实际报告必须采用目标仓库的真实名称。对象定义和流程的文件位置按前述规则写在代码注释中；其他定位信息放在证据列或段落末尾。

报告正文开头必须先写 `项目地址：<GitHub URL>`。地址必须来自用户提供的链接或仓库 Git remote 的核验结果；无法核验时写 `项目地址：未发现可核验的 GitHub 地址`。记录分析日期、分支或提交，以及影响结论的未提交改动。

1. 分析范围、业务主线与部署方式

先说明框架解决什么问题，再区分业务主线、部署方式、主线内的处理分支和实现版本，不能把这些维度混成一张版本清单。

业务主线按对外 API 背后的真实处理链判断。若几组 API 的底层处理互不相交，可以各自拆成独立程序，就用不同的大标题分别分析各自的对象、数据流、接口和代码结构；不要把它们拼成一条主线。只有一条主线时按一条介绍，不因接口前缀、Agent 后端或运行分支不同而强行拆分。

部署方式说明同一主线如何在不同进程、机器或环境中装配，例如本地和云端。分别交代入口、运行位置、依赖、共享能力和部署专用组件；两种部署复用底层逻辑时，复用部分介绍一次，在各部署下说明差异。

可用场景表辅助交代范围：`| 业务主线 | 部署方式 | 入口与执行位置 | 主要能力 / 分支 | 实现状态 | 本次是否展开 |`。多版本、可选接入和主线内分支应明确标注，不能冒充独立业务主线或新的部署方式。

后续对象、流程和接口都要能对应所属主线与部署。仅提供库、SDK 或命令行而没有独立 server 时，说明实际调用边界，不虚构网络接口。

2. 名词表

名词表最后撰写。先完成对象、数据流、接口和代码文件结构的分析与正文，再从不了解项目的读者视角通读全文，找出影响理解、需要事先知道的概念，最后补写名词表。撰写顺序与正文展示顺序不同：写完后，名词表仍可放在正文前部供查阅。

名词表只收录贯穿多个对象或章节、理解整体系统必须知道的大概念。例如 SessionID 频繁出现在输入、事件、存储和接口中，可以解释它如何关联同一条会话。不能把对象清单、字段清单或所有代码名字搬进名词表。

与具体对象或所处位置强相关的名词，应在对应数据对象下结合职责、关系和使用场景解释。例如 HostInfo 是主机身份与状态记录，应随主机对象及其连接、路由关系介绍；不能因为正文提到了它，就再在名词表解释一次。数据对象章节已解释的内容不在名词表重复，必要时用简短引用指向对应位置。

名词表使用无序列表，每个概念一个条目，统一格式为“通用名词（本仓库的叫法 / 代码名字）：解释”；名词和代码名字可加粗，代码名字使用行内代码格式。

例如：

- **会话标识（`SessionID`）**：SessionID 标识一条持续对话，输入、事件、存储和后续请求通过它关联同一条会话。

解释应有完整的主语、谓语和宾语，用通用计算机知识说明含义。同一概念有多个叫法时，在同一条目的括号中列出；不同概念应分别说明。通读后若没有确实需要预先解释的跨对象概念，可以省略名词表，不为凑章节重复正文。

3. 数据对象

3.1 找到贯穿会话的主体

从新建会话入口、后续输入入口和历史恢复入口查找贯穿会话的对象。它可能叫 Session、Conversation、Thread 或其他名字，也可能由多个对象共同承担，不能仅凭名称判断。

说明这个主体如何标识一条会话、保留什么上下文、关联哪些运行组件，以及多轮请求如何找到同一条会话。区分会话标识、内存中的会话对象、持久化记录和一次运行的状态：它们可能互相关联，但生命周期和职责不同。

运行时数据通常围绕会话组织，但不一定都直接挂在会话对象上。应根据真实持有、引用、共享和查找关系说明数据在哪里；若框架没有统一的会话对象，明确说明哪些对象共同承担这些职责。

3.2 按主分类组织对象

同一主线有多种部署方式时，先以“共享与部署无关的对象”“本地部署的对象”“云端部署的对象”等标题区分适用范围，再在各范围内按主分类设置子标题，并在分类下介绍对象。具体部署方式按仓库事实命名，不能固定套用本地 / 云端。不同业务主线的对象应先放到各自主线的大标题下，再采用这一组织方式。

以真实创建、持有与使用关系判断部署归属，不按目录名或类型名猜测。例如 LocalRuntime 可能被本地和云端同时使用，daemon 包中的启动参数也可能被云端配置复用；这类对象放共享部分。仅某种部署装配的对象单独介绍，并说明它如何引用共享对象。一个对象完整介绍一次，其他部署只引用并说明配置或使用差异。

3.1 已经展开介绍的会话主体及相关对象，后续按主分类介绍时不再重复设置对象标题或介绍职责、字段、结构和生命周期；只介绍前文尚未展开的对象。需要说明分类或关系时，用一句话引用前文即可。此规则同样适用于 3.1 中一并介绍的会话记录、会话配置等对象，不能只按章节标题去重而遗漏它们。

先沿会话主体的持有、引用、创建和使用关系确定关键对象，再按主要职责归类。下面八类是分类依据，不是按类别找对象填满的选取清单；未发现相关对象的类别可简要说明核查结果。

在已区分的主线与部署范围内，以主分类划分子标题，在每个分类下面，再为对象设置下一级标题，统一使用“代码名字（通用语义：xxx）”，例如“LocalRuntime（通用语义：一个 Host 进程的业务内核）”。对象清单、分类说明和对象职责不要用总表或分类表呈现；同一对象采用一个主分类，其他作用在该对象下说明。

以下分类含义供分析时判断，报告应将实际对象放到对应分类下展开：

#### 程序控制类

对象协调程序执行的顺序、并发和中断，本身不表达用户业务内容。

锁、通道、取消信号、并发门限、Redis 互斥锁等。说明它保护或协调哪个会话行为，不展开底层实现细节。

#### 存储对象类

对象提供数据读写能力，连接内存中的会话与数据库、文件或对象存储。

本地和云端的存储接口、数据库访问对象、历史读写组件等。说明它读写哪些对象、落在哪里，以及何时读写；业务记录本身归业务数据类。

#### 配置类（启动配置）

对象由环境变量、配置文件或编译脚本等在启动前后静态加载，决定服务如何启动和提供能力。

全局默认模型、服务地址、存储位置、启动功能开关等。说明作用范围和加载时机，不把后续请求携带的会话设置混进来。

#### 业务数据类

对象表达用户和其他服务关心的会话内容、过程或结果，主要承载数据，通常会持久化。

用户输入 prompt、消息历史、会话事件流、工具调用记录、运行结果、产物引用等。说明这些内容如何产生、变化、保存和对外呈现。

#### 会话配置类

对象在首次会话请求或后续配置接口中传入，承载一条会话的运行配置、控制属性和标识信息。

会话标识、模型配置、技能说明、工具权限、工作区选择等。说明配置如何定义这条会话的特点，是否可更新，以及更新从何时生效。

#### 网络模块类

对象承担基础网络传输、路由、输入格式校验、消息收发或连接维护。

HTTP / WebSocket 接入层、消息路由、传输连接等。说明它把请求交给谁、把结果送到哪里；带有业务决策的 client 或适配器不能仅因发网络请求就归入此类。

#### 基础组件类

对象提供多个业务都可复用的底层能力。

定时器、连接池、内存池等。只说明它为会话提供的支撑及共享范围，不把通用设施当作 Agent 专有能力展开。

#### 组件对象类

对象封装本业务专用的一组数据和操作，有自己的接口或模块，能够独立承担一项能力。

沙箱控制、Agent 执行、上下文管理、工具调度等组件。说明它管理什么、提供什么能力，以及如何与会话配合；其业务数据另列并关联。

分类以职责为准，不能只看类型名或是否有方法。同一个定时器用于中断超时运行时可归程序控制，作为共享调度设施时可归基础组件；连接池也应按其实际职责选择主分类，并注明其他作用，不重复算作多个对象。

会话配置属于运行时配置。应区分启动默认值、请求携带值和会话实际生效值，按代码说明继承或覆盖关系。同一份信息同时出现在请求、内存和持久化记录中时，要说明它们是同一业务信息的不同表示，还是各自独立的对象。业务数据是否持久化、会话配置是否支持热更新，都必须核实，不能按常见做法推断。

3.3 分类下的对象介绍

在对应主分类的对象标题下，直接用精简代码定义展示关键成员，并在成员旁用注释解释业务职责和关系。对象承载的数据、配置与组件都在代码中呈现，不另写“主要数据：成员、Agent 句柄、队列……”这样的文字清单，也不把同一对象拆成一处文字摘要、一处代码详解。生命周期、证据及无法在代码中清楚表达的边界紧随代码补充；同一对象沿用已有分类和标题集中介绍。前文已介绍的对象用引用衔接；补充细节回填到已有介绍，不在后续章节重新展开。

代码只保留能解释业务作用的核心字段、关联对象或接口，以注释说明输入内容、历史、运行状态、环境身份等含义；不在代码外再次枚举这些内容。对象可以是记录、集合、模块或远端资源，不限于类；接口型对象直接展示接口与职责注释，没有统一结构时可用明确标注的字段投影或关系伪代码，不能虚构真实字段。

对会话主体、核心业务数据、会话配置和主要组件，优先在伪代码注释中说明下列内容；不便通过结构表达的部分再用文字补充：

- 对象由谁创建或加载、由谁更新或销毁，是服务共享、每会话一份，还是每次运行临时创建。
- 对象的关键数据从哪里来，被哪些组件或外部服务使用；哪些仅在内存存在，哪些持久化，以及如何恢复。
- 对象提供什么独立能力，或仅承载什么数据；如果没有它，具体哪一步无法完成或需要由谁接替。

职责解释要落到实际系统行为。例如，沙箱控制组件负责申请、复用和释放执行环境；执行环境对象记录某个环境的身份、工作区和可用状态。前者管理环境，后者代表被管理的环境，不能笼统地都写成“管理沙箱”。

4. 对象关系

数据对象介绍完成后，用独立的大标题分析对象之间的关系，再进入主体对话数据流。选择紧密协作或名称、职责相近而容易混淆的对象分组介绍，例如 LocalRuntime 与 Session；不穷举所有对象的两两组合，也不重复已有对象定义。

4.1 先说明结构与对应数量

每组使用相关对象名字作为子标题，先核实并说明继承或接口实现、组合、包含、引用、按标识查找和共享等结构关系。明确谁持有谁、谁创建或管理谁；不能把目录包含关系、方法调用、Go 的字段嵌入或指针引用直接称为继承。

接着说明关系两端的对应数量：一对一、一对多、多对多，以及是否允许零个。交代数量关系成立的范围，是单个进程、单条会话、某次运行、持久化身份，还是跨主机副本；区分同时存在的关系与随时间更替的关系，不从一个字段就推断系统全局唯一。

例如，应核查一个 LocalRuntime 是否管理多个 Session、一个本地 Session 是否引用一个所属 Runtime，以及共享存储和 provider 是否由 Runtime 统一提供。实际关系必须来自目标仓库，不能把这一例子当作所有框架的固定结构。

4.2 再说明数据链路中的协作

结构关系讲清楚后，指出这些对象在哪条业务主线、部署方式和具体数据链路里串起来协作，例如会话接纳、成员创建、输入执行、事件保存、订阅、恢复或资源释放。用短流程伪代码展示谁获取或创建谁、哪些数据在对象间传递、谁修改或保存数据，以及结果交给谁；每段仍只标注一个主要实现文件。

这里只展示理解对象关系必需的协作步骤，完整处理过程放在后续主体对话数据流中。共享组件按会话标识查找资源时，要写成查找或引用关系，不能画成每条会话独占一份。

4.3 最后说明区别与生命周期边界

对于相似对象，结合刚才的结构和协作说明差异，例如运行对象与持久记录、配置描述与活跃句柄、控制组件与被控制资源。交代创建、释放、失效与保存的边界，说明一个对象结束是否影响另一个对象。

关系章节用对象组合的子标题、短说明和必要的关系或流程伪代码呈现，不使用对象关系总表。继承、持有、基数、协作链路和差异都要能追溯到源码；没有依据的对应数量明确保留为未确认项。

5. 主体对话数据流

5.1 新会话入口与主要分支

找到用户第一次创建会话并开始对话的真实入口。若“创建空会话”和“提交首条输入”是两个接口，应串起来说明，不能把空会话创建成功当作对话已开始。

列出入口中的主要分支，例如新建或恢复、本地或远程执行、不同 Agent 后端、不同运行模式。使用表格：`| 入口与分支 | 触发条件 | 获取或创建的核心对象 | 主要行为差异 | 实现状态 | 是否作为主线 |`。只列代码中真实存在的分支。

优先选择常用且实现最完整的分支展开，说明选择依据。默认分支与最完整分支不一致时，明确差异，并说明后续主线采用哪一个；不要将可选或实验能力写成默认行为。

5.2 按数据变化展开一次完整请求

从首条请求进入服务开始，按实际先后顺序介绍处理过程，直到用户收到结果、此次运行结束，以及相关数据完成保存。可以将阶段拆成接入校验、查找或创建会话、形成有效配置、准备运行资源、组织模型输入、模型与工具执行、输出事件、收尾保存等，但必须按真实实现调整。

每个阶段都交代以下内容：

- 输入是什么，来自用户请求、已有会话、启动默认配置，还是外部服务。
- 获取了哪些已有对象，在哪里创建或派生了新对象；获取失败时怎样影响后续步骤。
- 对哪些对象执行了什么操作，产生了哪些内容或状态变化。
- 哪一步发生本地读写、进程操作、数据库访问或远端请求；哪些必须等待，哪些在后台继续。
- 结果流向哪个对象、存储位置或外部调用方，以及何时对用户可见。

优先用分阶段伪代码串联完整请求，把上述信息放在赋值、分支、循环和注释中。长流程按创建、执行、输出、收尾等实际阶段拆成多个短代码块；同一段代码中标明同步等待、后台执行和失败后的行为。分支比较、状态归属或接口总览可以用表格补充，避免再用表格或长段落逐步重复整条主线。

例如，先通过沙箱控制组件获取已有或新建的执行环境对象，再将环境标识与会话关联，并用该环境执行工具任务。应核查环境何时真正可用、任务结果写入什么业务数据、通过什么事件呈现给用户，不能只写“初始化沙箱并执行 Agent”。

模型和工具可能反复交替执行，应说明每轮如何补充输入、产生工具请求、保存执行结果并决定继续或结束。区分原始模型输出、内部业务事件、对外发送的事件和持久化历史；若存在转换、过滤、合并或丢弃，说明具体发生在哪一步。

5.3 会话延续与关键中断

在主线之后，用条件分支或短伪代码说明与对象生命周期直接相关的差异：后续输入如何找到原会话并恢复上下文；会话配置更新后影响当前运行还是下一轮；取消、断连、失败或重启后保留什么、释放什么，以及是否能继续。

只分析真实存在且影响主线理解的行为，不穷举底层异常。特别区分一次运行结束、网络连接关闭和会话结束，它们不一定导致相同的数据清理。未实现或证据不足的恢复、重放、去重行为应明确说明。

6. 接口语义

6.1 先确定对外接入面

优先介绍服务实际提供的 HTTP 接口。存在 HTTP 接口时，以这些接口说明对外能力；Go 库等编程接口只用一句话说明存在及用途，不逐项展开导出方法、内部调用或接口签名。没有 HTTP 接口时，才改为介绍实际公开的 RPC、协议消息、命令行或库入口；用户明确要求分析这些入口时按其要求展开。

根据实际部署与调用边界分节，标题必须明确接口类型。例如项目同时提供本地与云端服务时，分别使用“本地 HTTP 接口”“云端 HTTP 接口”“其他接口”。只有真实存在不同接入面时才分开，不能把同一套接口重复列两遍，也不能把可选实现当作默认接口。其他协议通常只概述使用者、用途及与 HTTP 的关键差异。

6.2 按类型和业务职责设置接口子标题

接口章节不用表格。每个接入面标题下，再按会话管理、输入与运行控制、成员管理、历史与事件订阅、环境与资源、服务检查等实际职责设置子标题，标题明确写出接口类型，例如“会话管理类 HTTP 接口”“Host 连接类 WebSocket 接口”。具体接口用更下一级标题“HTTP 方法 + 路径：职责”介绍；语义一致的查询或别名入口可以在同一条中说明。

每个接口用简短段落说明调用时机、关键输入、操作哪些业务对象、返回什么，以及返回成功表示哪一步完成。保留真实方法和路径，必要时说明普通 JSON、持续事件流与 WebSocket 升级的区别；不要转写成内部 Go 方法清单。健康检查等通用接口可简写。

同一个项目的本地、云端或可选 HTTP 实现即使路径相同，也要核对请求体、响应形态和完成含义；共享接口引用前文，只展开差异。没有外部路由的内部能力，不能依据库方法的存在虚构一个 HTTP 接口。

6.3 关键接口的行为边界

重点解释与主对话链路有关的接口：

- 接口创建的是会话、一次运行还是一条输入；接收成功、资源准备完成和执行结束分别如何表达。
- 接口依靠哪些标识找到对象，对对象执行创建、读取、修改、删除还是触发运行；对象不存在或状态不允许时如何处理。
- 接口是同步返回结果，还是先返回标识后异步执行；执行进度与最终结果通过哪个接口或事件取得。
- 配置更新、取消、删除和断开订阅各自影响什么对象，是否影响正在执行的任务、持久化历史和关联资源。

将接口和前文对象、数据流阶段对应起来，使读者能从一个 HTTP 入口找到它操作的对象及数据变化。权限、重试、游标和完成边界应结合对应接口说明，避免脱离使用场景再罗列一套内部接口。请求只是提交成功时，不能写成任务已完成；内部存在的能力但没有外部入口时，应明确说明。

7. 代码文件结构分析

7.1 目录与关键文件

按仓库真实目录层级展示与本次主线相关的代码，以目录树或保留层级的表格呈现，并解释关键目录和文件在整个系统中的职责。保留实际路径和文件名，让读者能把前文的对象、数据流和接口定位到代码；不要只列目录名称或逐行翻译文件注释。

重点覆盖真实启动入口、接口注册与接入、会话主体及相关业务数据、会话编排、模型与工具执行、业务组件、配置和持久化等代码位置。按仓库实际组织取舍，不强行套用这些目录名；同一文件承担多个职责、同一能力分散在多个目录时，都应如实说明。

用表格说明：`| 目录 / 关键文件（保留层级） | 系统职责 | 关联对象（代码名字） | 对应的数据流阶段 / 接口 | 所属场景 / 版本 |`。

只展开足以理解主线和模块边界的层级，保留承担关键职责的具体文件。通用测试、工具、生成文件和依赖目录可省略；如果它们决定能力是否被构建、注册或启用，则说明其作用。路径和职责应通过实际内容及使用关系核验，不能只根据目录名推断。

7.2 代码组织与业务关系

说明主要模块如何配合：入口如何装配会话及其组件，哪些模块定义或保存数据，哪些模块负责操作这些数据，以及模块间有哪些直接依赖或共享能力。将这些关系对应到前文的对象层级和请求流转，不把文件目录上的包含关系直接当作运行时对象的持有关系。

多个包、服务或 Agent 后端分别承担主线的一部分时，说明各自边界和连接位置；新旧实现、未接通代码和当前主线应有明确区分。读者应能沿着代码结构找到首次创建会话、模型与工具执行、事件输出和保存收尾的关键位置。

8. 证据与未确认项

关键对象、主线步骤和接口都应能通过只读源码追溯到当前实现。代码名字用于定位对象，证据引用用于核对定义、真实调用入口、状态变化与持久化路径；不能仅凭文档或类型声明认定完整链路已经接通。

结论区分“源码确认”“源码推断”和“证据不足”。对未接通的分支、未使用的对象或仅有设计的接口，根据代码说明依据；源码无法确定的外部服务行为和运行效果写明边界，不通过执行测试或启动服务补证，也不把缺少运行结果当作未实现。

完成前检查：对象关系独立成章，先说明结构与对应数量，再说明协作链路及易混区别；独立业务主线已用不同大标题区分；对象按共享部分与实际部署方式分节，专用对象未混入共享部分，共用对象没有按部署重复介绍；分析仅采用只读源码方式，没有运行项目测试或服务，报告没有测试命令、结果或输出附录；接口以实际 HTTP 接入面为主，按类型设置子标题且没有使用表格；有 HTTP 接口时，Go 等库入口未逐项展开；每个代码对象定义前均有已核验且不带行号的文件注释，每段流程已标注一个主要文件；名词表在正文完成后经通读补写，仅保留必需的跨对象概念，使用无序列表，且没有重复数据对象中的解释；每个对象的关键成员和承载数据均由代码及注释展示，没有“主要数据：……”等文字枚举，也没有分散重复的对象摘要和详解；数据流优先使用顺序与分支伪代码，文字未重复枚举字段或步骤；对象按主分类及对象标题组织，没有使用对象总表或分类表；前文已展开的对象未在后续分类下重复介绍；分类边界清楚，层级与生命周期有依据；主线覆盖首条输入到输出及保存；接口能对应对象和数据变化；目录和关键文件的职责与实际对象、链路一致；同一对象在各部分使用相同名字。分析多个项目时，分别生成报告，再用统一的通用名词对照各仓库对象、主要数据流和接口职责，保留实现差异。
