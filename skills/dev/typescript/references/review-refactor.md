# Review And Refactor Rules

审查、重构、迁移 JavaScript 到 TypeScript 或修复类型错误时读取本文件。

## 审查优先级

1. 会导致运行时错误、数据损坏、竞态或安全问题的缺陷。
2. 类型系统被绕过导致的真实风险，例如过宽的 `any`、错误断言、非空断言。
3. API 契约不清、错误处理缺失、异步流程不可靠。
4. 可维护性问题，例如重复类型、过大函数、命名误导。
5. 纯风格问题放最后，且应尊重项目现有 formatter。

## 审查输出

- 先列发现的问题，按严重程度排序。
- 每条问题给出文件和行号。
- 说明为什么这是问题，以及可能的最小修复方向。
- 没发现问题时明确说明，并指出剩余测试风险。

## 重构原则

- 保持行为不变，除非用户要求修 bug。
- 小步修改，避免同时做风格整理和行为改动。
- 优先收紧边界类型，而不是在内部到处断言。
- 用类型守卫或 schema 校验隔离外部输入。
- 把重复的对象形状提成接口或类型，但不要过早抽象。

## JavaScript 转 TypeScript

- 先识别模块边界、输入输出和外部依赖。
- 为公共函数、导出对象和外部数据添加显式类型。
- 内部局部变量尽量让 TypeScript 推断。
- 对未知外部输入使用 `unknown`，再收窄。
- 避免为快速通过编译大量添加 `any` 或 `as`。
- 迁移后运行类型检查和现有测试。

## 类型错误修复

- 优先修正真实类型建模，不优先压制错误。
- 不用 `// @ts-ignore`，除非有明确原因和后续清理计划。
- 不用非空断言隐藏生命周期或数据流问题。
- 如果错误来自第三方类型缺陷，将 workaround 收敛到边界层。
