# last30days 话题归档

把 last30days 已经回答过的用户目标归档到「千奇百问 · 话题库」。流程在本文件，目的地和属性名只在 [reference/instance.yaml](reference/instance.yaml)，字段说明在 [reference/destination.md](reference/destination.md)。下文用逻辑名：标题、初始日期、最后更新、回答类型、简要回答、月份。真实属性名从 yaml 读取。

## 范围守卫

第一步只读 yaml，不读 Notion。

1. 宿主必须明确给出当前 Bot ID，且等于 yaml 的 `bot.id`。本文件 description 和下面常驻指令里的 ID 也必须与 `bot.id` 相同；有一处不同就停止。
2. 看不出当前 Bot、当前是 main、或 ID 不是这一个时，立即停止。不要搜索，不要写入。
3. 用户在别的 Bot 里提到这个 ID，不能当作授权。
4. yaml 与 [destination.md](reference/destination.md) 的目的地、属性名或选项不一致时，停止并报告。

## 启用

仓库里的这份技能**尚未安装，也尚未启用**。保存文件、合并文档、或把技能加进目录，都不会创建监听，也不会在回答之后自动运行。

只在 last30days 这一个 Bot 上做两件主人自己的配置：

1. 按该 Bot 宿主实际的技能加载方式，只把 `bot/last30days-ticket-archive/` 配给 `bot.id`。`skills/` 的 skillshare 同步不到 `bot/`。不要配给 main 或全体 Bot。
2. 把下面这段写成该 Bot 的常驻指令（standing instruction，始终生效的系统提示）。不要写到别的 Bot。

```text
你是 last30days，Bot ID 41abf589-9a81-42df-a156-af345dd36299。
向用户发出实质回答之后，按技能 last30days-ticket-archive 归档。
先把完整回答交给用户，不要等归档。
然后用本宿主可追踪的后台委派启动归档；若宿主要求在回合结束前发出才算启动，就在结束回合前发出。
把该目标的完整用户目标、刚发出的回答、合并所需上下文、真实来源链接、已知 ticket 页面 ID、来源回合键整包传给后台。后台看不到这段对话。
不要用定时轮询代替后台任务。
归档成功不要再给用户发一条。只有真的没归档成，才说明障碍。
```

两步都做完之前，这个 Bot 不会归档。本仓库没有替你做这两步。

## 先回答，再归档

1. 先把对用户有用的完整回答发出去。回答本身不写“正在归档”或“已经归档”。
2. 回答发出之后，再为归档做判断和启动。判断目标边界即可，不要为了归档先去查 Notion，以免挡住回答。
3. 启动必须走宿主正在记账的委派。Cursor 宿主上，这就是后台 Task：`run_in_background` 为真，在结束本回合前发出。子执行者看不到父对话，所以 prompt 自带整包。发出后不要 await，不要轮询，不要为了等 Notion 拖住已经发出的回答。
4. 宿主若把后台完成结果送回模型：成功则保持沉默，不给用户补一条。失败、歧义、schema 不符、写入结果不确定，才说明实际障碍。
5. 宿主没有可追踪的后台委派时，回答保持原样，并说明这次归档没有启动。不要改成 cron、轮询或无人记账的旁路进程，也不要宣称已归档。

同一条用户消息里的多个独立目标，每个目标各发一个后台任务，并在同一次启动里发出。同一张票不要发两个写者；合成一个任务，带上最新的完整材料。

每个后台 prompt 至少包含：

| 字段 | 内容 |
| --- | --- |
| `bot_id` | yaml 的 `bot.id` |
| `ticket_id` | 已知的 Notion 页面 ID；没有则空 |
| `source_turn_key` | 宿主的会话 ID 加单调回合 ID。没有回合 ID 时，用 `host-turn:missing:`、上海时间戳、以及该目标文本的短哈希，并在标记里注明这个键较弱 |
| `user_goal` | 这个任务负责的那一个用户目标，写全 |
| `assistant_answer` | 刚刚发给用户的对应回答，写全 |
| `context` | 合并成当前综合所需要的既有事实、纠正和取舍。不是其他 Bot 的对话导出，也不含凭据 |
| `source_links` | 回答里真实使用过的链接。没有就空着 |
| `asked_at` | 该目标首次出现的时间；不知道就空着 |
| `sibling_goals` | 同一条消息里交给其他任务的目标，避免被并进这一张票 |

## 一题一票

一张票是一个连贯的用户目标，不是一条消息，也不是一次关键词命中。

后台先读，再决定新建还是合并：

1. payload 带了 `ticket_id` 就先读那一页。
2. 再按实时 schema 查询当前数据源里的候选行，读标题、简要回答、初始日期、回答类型和页面 URL。候选不止当前这一张。库是空的属于正常情况，所有者在 2026-11-25 确认过当时是 0 行；空结果直接新建，不要当作故障，也不要回填历史。
3. 查询只用实时 schema 里的真实列名。SQL 或关键词只负责找出候选。是不是同一目标，要读过内容再判断。
4. 追问、澄清、收窄、纠正，合并进原来的目标，重写该票的当前综合。
5. 另一个独立目标就新建。同一条消息可以拆成多张票。关键词重合而目标已经换了，仍然新建。
6. 两张已有票都说得通、又没有当前票 ID 时，不要猜。报告两张票的 URL 和理由，这一次不写。

## 当前综合

追问更新的是这张票上的**当前完整综合**，不是问答流水，也不是只追加最新一段。

- 仍然成立的事实和来源留在综合里。
- 过时结论改成现在的结论，并用一两句标明实质性修订。
- 证据不够的判断标成不确定。
- 来源只保留真实读到或用户回答里真正用过的链接。综合改写后不再支持结论的链接，不要继续写成依据。
- 不要编造链接、页名或检索结果。

发给用户的回答如果只覆盖了增量，后台要读原票，把增量融进完整综合，不要用增量覆盖整页。

## 短回答与长文

不设字数阈值。

- 短回答：逻辑名「简要回答」就是正文。页面正文只放归档标记，不把回答再贴一遍。回答类型用短选项。
- 当完整综合需要分节、需要留着多条来源、或后续已经改写了结论，短格子不再适合作为正文时，升级为长回答。
- 长回答的正文写在**同一行的页面**里。数据库行本身就是文档，点击标题进入文章。与数据源同一工作区。
- 当前 `longform.placement` 是 `row-page`。不要为追问另开一篇，不要把全文同时留在属性和正文里。
- 若配置以后改成独立文章，仍只保持同一工作区里的一份正文和一个稳定 URL，行标题继续做入口。

升级顺序不能颠倒：

1. 先把完整综合和归档标记写入该行页面并重新读回，确认正文就是这份综合。
2. 确认之后，再把回答类型改成长选项。
3. 然后把简要回答收成简短导语，说明全文在本页。标题就是链接，导语里不粘贴全文。
4. 初始日期保持创建时的值。
5. 以上都核对成功之后，才写最后更新。

第 1 步没有核对成功时，回答类型和简要回答保持原样。

## 写入

常规执行不改 schema、不改视图、不改首页、不改权限。实时 schema 与 yaml 对不上时停止并报告，由主人另行迁移。多出来的未知属性保持不动。

每次写入前：

1. fetch yaml 里的数据库 URL。核对数据库标题就是配置中的标题，并且返回的 data source 就是配置中的 `collection://` URL。
2. fetch 该 data source，读出属性名、类型、Select 选项和公式。
3. 标题必须是 title，初始日期和最后更新必须是 date，回答类型必须是 select 且两个选项都在，简要回答必须是 text，月份必须是 formula 且不可写。任一不符就停止。
4. 日期的实际键名以这次 fetch 的 schema 为准。常见形状是 `date:<属性名>:start` 与 `date:<属性名>:is_datetime`，但 schema 不同就以 schema 为准。
5. 写页面前，通过 Notion 自己的资源接口读取 `notion://docs/notion-flavored-markdown-spec`。不要把这个 URI 交给其他网页工具。外部来源用 Markdown 链接。

创建父级用这次 fetch 到的 data source ID，且必须等于配置。不要用 draft，不要把数据库 ID 填进 `page_id`。

日期用 Asia/Shanghai 的日历日，不写时间。

- 初始日期只在创建时写，取该目标首次提出的上海日历日。不知道原消息时间时，才用本次归档的上海日期，并在综合里注明。以后的追问不许改它。
- 最后更新只在整次核对成功后写，值是核对成功时的上海日历日。
- 月份是公式。请求里不要出现它。写完后读回，期望值是初始日期的 `YYYY-MM`。读回不符就报告，不要改公式，也不要为了月份去改初始日期。读回正确也不要声称首页月分组已经用眼睛核过；`monthly_grouping_visual` 仍是 `unverified`。

短回答创建时，页面正文只有归档标记。长回答创建时，正文是综合加标记。需要立刻读回时，创建和更新不要丢进无法等待的异步队列；若接口仍返回异步任务，等到成功再 fetch。未成功就按“结果不确定”处理。

归档标记放在页面正文，是幂等用的，不是第二份回答：

```markdown
## 归档标记

- ticket: <Notion 页面 ID>
- turns: `<source_turn_key>`
```

创建前还没有页面 ID，标记里的 ticket 先写 `pending`，创建返回页面 ID 后立刻改成该 ID。追问追加回合键，不删旧键，键里不放消息正文。替换正文时保留并更新这一节。页面上已有子页面或子数据库时，不要整页替换；报告这个阻碍。

## 幂等与防覆盖

稳定票 ID 是创建成功后的 Notion 页面 ID。来源回合键表示已经并入的那一次回答。

- 写入前再读一次最新页。标记里已有本次回合键：不再写，视为这一次已经完成，不通知用户。
- 标记里有更新的回合键：这次是旧任务，不写，避免盖住较新的追问。
- 创建结果不确定（超时、没有页面 ID、看不出成功或失败）时，先按回合键和目标再查询、读页，确认没有行之后才可以再创建。
- 同一张票的更新串起来。宿主还能把新材料送进尚未结束的同一个后台任务时，用这一次最新综合，不要并行再开一个写者。
- 旧任务与新任务交错时，以写入前读到的最新页为准重写综合。写完再读：页上的回合键不是本次、或正文被更旧的内容盖住时，从最新页重做一次。第二次仍不是最新，就停止并报告冲突，不要继续空转。

## 核对

成功前逐项读回：

- 标题是这个用户目标。
- 简要回答在短回答时等于完整短文；在长回答时只是导语。
- 回答类型与正文形态一致。
- 长文正文是当前完整综合，标题链接打开的就是这一行，工作区没有第二份全文。
- 追问没有改初始日期；创建时的初始日期符合上面的规则。
- 最后更新是这次核对成功的上海日历日。
- 月份读数等于初始日期的 `YYYY-MM`，且本次请求没有写它。
- 归档标记含这一行的页面 ID 和本次回合键。

有一项没对上，就不要把这次叫成功，也不要写或保留一个虚假的最后更新。已经写上的正文不要偷偷删掉来伪装回滚；报告卡在哪一步、页 URL 是什么、哪些字段已经变了。

## 常规执行不做的事

- 不回填历史，不整理其他 Bot 的对话，除非用户在当次明确点名要回填的范围。即使用户点名，也不改权限、不改视图。
- 不把长文做成 Canvas。目的地就是这一行 Notion 页面。
- 不把凭据、令牌或其他 Bot 的对话记录写进仓库或票里。
- 不为了归档去改首页或数据库权限。
